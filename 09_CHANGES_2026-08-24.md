## Issue 1 — Options never received live prices in SIMULATOR mode (root cause of "only ATM updates" / "P&L doesn't update live")

**Root cause:** `backend/app/market_data/simulator.py`'s tick loop only generated quotes for the 5 index *futures* (`NIFTY-FUT`, `BANKNIFTY-FUT`, ...). Every actual tradeable instrument is an **option** (`OrderService.place_order` rejects anything that isn't `InstrumentType.OPTION`), and nothing ever called `MarketDataCache.set_quote()` for an option symbol in local/simulator mode. This was in fact already called out as a known limitation in `07_HOW_TO_RUN.md` ("option contracts won't have a live premium") and reproduced in the troubleshooting section ("No live market data available... In SIMULATOR mode this is expected for options").

Consequences of the gap:
- Every option in the chain showed `ltp: null` — the only price that ever appeared to move was whatever underlying/index price the top ticker strip happened to be reading, which reads as "only the index/ATM price updates."
- **Every order was rejected** with `"No market data available"` (`matching_engine.py`) — the buy/sell flow was non-functional against the simulator, not merely slow.
- `PnLEngine.mark_to_market_account` silently `continue`s past any position with no cached quote — floating P&L for a real open position could never update, matching the "P&L doesn't update in real time" report exactly.

**Fix:** `simulator.py` now also loads all `OPTION` instruments from the DB (refreshed periodically) and, each tick, derives a synthetic premium per option from its underlying's simulated spot: intrinsic value (moneyness) plus a distance-decaying time-value component, quantized to the instrument's tick size. Each synthetic tick is cached, broadcast over the WS, and fed into the same P&L-push path the futures already used. This is a deliberately simple pricing curve (no IV/Greeks/Black-Scholes) — same tradeoff already accepted for the short-margin approximation in `core/config.py` — but it means every strike now has a live, moving, tradeable price.

**Files:** `backend/app/market_data/simulator.py`, `backend/tests/test_simulator_options.py` (new).

## Issue 2 — Accounts and orders had no ownership check at all

**Root cause:** `backend/app/api/accounts.py` and `backend/app/api/orders.py` didn't import or use `get_current_user` anywhere. `GET /accounts` returned every user's accounts with no filter; every `/accounts/{id}/...` route (summary, positions, closed positions, graduate, place/list orders) trusted the URL with zero check that the account belonged to the caller. Any authenticated user could read or trade on any other user's account by guessing/enumerating an account ID. (`trades.py` already had this check — it wasn't wired into the other two routers.)

**Fix:** Added `Depends(get_current_user)` to every route in both files, plus an ownership helper (`_get_owned_account` / `_assert_account_owner`) that 404s — not 403s — when the account doesn't exist *or* belongs to someone else, so a caller can't use the status code to enumerate valid account IDs they don't own. Admins bypass the ownership check (same pattern already used in `admin.py`).

**Files:** `backend/app/api/accounts.py`, `backend/app/api/orders.py`, `backend/tests/test_account_ownership.py` (new).

## Issue 3 — Forced re-login on every page refresh / occasional login errors

**Root cause, two separate bugs:**
1. `JWT_ACCESS_TOKEN_EXPIRE_MINUTES=15` with **no refresh mechanism at all**. The frontend's only response to an expired token was `"Session expired. Please login again."` — full logout, re-enter credentials. Across a normal working session this reproduces as "forced to re-authenticate every time I refresh."
2. `POST /auth/login` called `ensure_seed_data(db)` **on every single login request** — a bootstrap routine that runs `CREATE TABLE IF NOT EXISTS` for the whole schema and, on cold start, inserts an admin user, a demo user, challenge packages, and ~25 instruments, followed by a `db.commit()`. Beyond the unnecessary latency on every login, this is racy: two logins arriving close together (e.g. a double-submit) can both observe "row doesn't exist yet" and both attempt the insert, raising a unique-constraint `IntegrityError` — a plausible source of "login errors immediately after entering credentials."

**Fix:**
- Moved `ensure_seed_data` to run once in the FastAPI `lifespan` startup hook instead of per-request.
- Added a real refresh-token flow: `create_refresh_token`/`decode_refresh_token` (7-day TTL, distinct `type` claim from access tokens so one can't be used as the other), a new `POST /auth/refresh` endpoint, and `refresh_token` added to the login/register response. The frontend (`api.js`) now stores the refresh token alongside the access token and, on any `401`, silently exchanges it for a new pair and retries the original request once — the user only sees "Session expired" if the refresh token itself is invalid/expired (i.e. after 7 days of inactivity, not 15 minutes).
- Added `iat`/`jti` claims to both token types (previously absent — two tokens minted for the same user in the same second were byte-identical strings; harmless but not correct JWT practice, caught while writing the e2e test).

**Files:** `backend/app/api/auth.py`, `backend/app/core/security.py`, `backend/app/schemas/auth.py`, `backend/app/main.py`, `backend/app/db/bootstrap.py` (unchanged, just called from a different place), `frontend/src/services/api.js`, `frontend/src/App.jsx`, `backend/tests/test_auth_tokens.py` (new).

## Issue 4 — Config hardening (CORS / JWT secret)

**Root cause:** `main.py` registered CORS with `allow_origins=[..., "*"]` and `allow_credentials=True` together — browsers reject that combination anyway, and it's a CSRF-adjacent footgun if it ever did take effect. `JWT_SECRET_KEY` defaulted to a hardcoded string with nothing stopping a deployment from silently running on it.

**Fix:** CORS now reads an explicit, comma-separated allowlist from `CORS_ALLOWED_ORIGINS` (defaults to just the local Vite dev origins). Startup now raises immediately if `APP_ENV` isn't `development`/`test` and `JWT_SECRET_KEY` is still the shipped default — fails loud at boot instead of silently serving traffic with a guessable secret.

**Files:** `backend/app/main.py`, `backend/app/core/config.py`.

## Issue 5 — Full browser UI test (found via real end-to-end use, not code reading)

Installed Playwright + headless Chromium and actually drove the app in a real browser (register → trade → watch P&L → refresh) rather than only exercising the API. This caught two bugs that no amount of reading the code or hitting individual endpoints with known-good parameters would have surfaced, because they only show up when the frontend calls the backend the way it actually does:

**5a. `GET /instruments/meta/expiries` always 500'd in SIMULATOR mode.** It called straight into the live Upstox SDK regardless of `MARKET_DATA_SOURCE`, and `upstox_provider`'s background event loop is only ever set inside `connect()` (never called in SIMULATOR mode). Since the frontend fetches expiries *before* it can request an option chain, this 500 meant **the option chain panel never loaded for any index in SIMULATOR mode** — a more complete failure than "only ATM updates," it just never rendered at all, silently (only visible as a CORS-flavored error in the browser console, because an unhandled 500 exits before Starlette's CORS middleware can attach the header). Fixed by giving `OptionChainService.get_expiries` the same DB-fallback branch `get_option_chain` already had, and made the underlying Upstox REST helpers (`get_option_contracts`, `get_option_chain`, `get_option_quotes`) use the currently-running event loop instead of the `connect()`-only `self.loop`, so they can't crash on this class of bug again regardless of caller.

**5b. Every self-registered account failed on its first trade — win or lose.** `POST /auth/register` seeded its EVALUATION `RuleVersion` with `max_daily_loss_percent=0.00` and `max_drawdown_percent=0.00`. `RiskEngine.check_post_trade` fails the account when `drawdown_percent >= max_drawdown_percent`; at a 0% threshold that's `0 >= 0`, which is trivially true the moment any post-trade check runs, even with a winning position and zero actual drawdown. This was caught by placing a real order in the browser, watching Positions for a few seconds, and noticing the account badge silently flipped from `ACTIVE` to `FAILED`. Fixed by giving the self-registration rule the same sane values already used everywhere else in the codebase for EVALUATION rules (`db/bootstrap.py`, `api/admin.py`): 10% profit target, 5% max daily loss, 15% max drawdown. Note: this only fixes newly-created rule rows — any account that already exists against the old 0/0/0 `RuleVersion` row keeps referencing it until that row is deactivated/replaced; no data migration was run since I don't have visibility into any real deployed DB's state.

**Files:** `backend/app/api/instruments.py`, `backend/app/services/option_chain_service.py`, `backend/app/market_data/upstox.py`, `backend/app/api/auth.py`, `backend/tests/test_option_expiries.py` (new), `backend/tests/test_registration_rules.py` (new).

## Issue 6 — The frontend container never actually served anything under Docker Compose

Everything above was verified either via automated tests or manual `uvicorn`/`npm run dev` processes run directly on the host. When asked to check again because "live data isn't showing," I re-verified against **Docker Compose specifically** (`docker compose up -d --build`, the documented/recommended way to run this project) and found the `frontend` container was crash-looping on every single startup:

```text
Error: Cannot find native binding. npm has a bug related to optional dependencies...
cause: Error: Cannot find module '@rolldown/binding-linux-x64-musl'
```

**Root cause:** `docker-compose.yml`'s `frontend` service bind-mounted the entire repo root (`.:/app`) into a `node:22-alpine` (musl libc) container, which puts whatever `node_modules` you already have installed on your host OS (Windows, in this case) directly in the path the container reads from. Vite's bundler (rolldown) ships platform-specific native `.node` binaries; the Windows-built one on the host isn't usable inside an Alpine/musl container, and there is no fallback — the dev server throws on the very first request and never serves a single page. This means **none of the SIMULATOR-mode and manual-process fixes above were ever visible if you were running via Docker Compose** — the browser had nothing to load at all, regardless of what the backend was doing correctly underneath.

This wasn't caught until now because every verification pass before this one used manual host processes (`uvicorn` + `npm run dev` run directly), never the actual `docker compose up` path.

**Fix:** Gave the `frontend` service its own named volume (`frontend_node_modules`) mounted over `node_modules`, so the container's bind-mounted source no longer shadows a host-platform install with a container-platform one — and added `npm install` to its startup command so that volume gets populated with musl-correct binaries on first run. Verified by actually running `docker compose up -d --build`, confirming Postgres/Redis/API all report healthy, confirming the frontend serves `200` on `localhost:5173`, and running the full Playwright browser pass (registration → live ticker → option chain with real Greeks/OI → order fill against a live ask price → live-updating P&L → session-surviving refresh) against the real containerized stack, with real Upstox data, not SIMULATOR mode. All 9 checks passed, zero console errors.

**Files:** `docker-compose.yml`, `07_HOW_TO_RUN.md`.
